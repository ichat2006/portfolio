GT Movies Store description

The application is organized around the required user stories for a movie storefront. The Movies screen lists the available movies and includes title search so users can quickly find a specific movie. Each movie detail screen shows the movie's name, description, price, image, quantity selector, and existing reviews so a user has the information needed to decide whether to purchase it.

  • Accounts: users can register, log in, log out, and access account-specific functionality.
  • Movies and search: users can browse the movie catalog, search by title, and open a detailed movie page.
  • Shopping cart: users can add one or more copies of a movie, review their cart, adjust what they plan to purchase, and proceed to checkout.
  • Orders: authenticated users can complete purchases and view their order history.
  • Reviews: authenticated users can create reviews and edit or delete reviews that they own.
  • Reporting: authenticated users can report another user's inappropriate review. Reported reviews are filtered from the public movie page and remain available for administrative management.
  • Administration: Django Admin provides management of application data such as users, movies, reviews, and orders.
  • Responsive access: shared Bootstrap-based templates keep the main workflows usable at different browser sizes, and PythonAnywhere makes the application accessible over the web rather than only on localhost.

Process description

I primarily followed the step-by-step process in Django 5 for the Impatient to build the core application. I worked through the project incrementally instead of trying to implement the entire site at once: I set up the Django project and apps, created models, connected URL patterns to views, built templates, added authentication, and then implemented the cart, checkout, order, and review workflows as I progressed through the textbook.

My usual development loop was to implement a small feature in PyCharm, run the site locally, test the specific page or action, and resolve the error before moving on. When I had questions or doubts, I compared my code with the textbook's structure and used Django's detailed development error pages to identify the failing file, template tag, URL, or line. This helped me work through issues involving static CSS/images, template block nesting, URL reversing, model migrations, and authenticated-user permissions.

For requirements beyond the basic textbook flow, I extended the existing Django design. The main example was inappropriate-review reporting: I added a reported state to the review model, created the report route/view, added a Report action for reviews written by other users, filtered reported reviews from public movie pages, and made the review state manageable through the administrative side. I tested this with multiple accounts so review owners retained edit/delete controls while another authenticated user could report the review.

Deployment was another major part of the process. I pushed updates with Git, updated the project on PythonAnywhere, ran migrations, checked the Django configuration, configured the hosted application, and reloaded it after changes. When the hosted site behaved differently from localhost, I used PythonAnywhere's error logs to trace settings, WSGI, and deployment problems. I then tested the final user flows on the deployed version rather than relying only on the local development server.
